# Contributing to DPadBridge

Thanks for helping make the web work better with a TV remote. Bug reports with a minimal HTML reproduction are as valuable as code.

## Setup

```bash
git clone https://github.com/DivProGamez/dpad-bridge-sdk.git
cd dpad-bridge-sdk
npm install
npm test            # unit tests + dist freshness check
npm run test:e2e    # Playwright, headless Chromium (run `npx playwright install chromium` once)
npm run demo        # http://localhost:8080/examples/tv-demo/
```

Node 18+ is required. The runtime library has **zero dependencies**. The dev dependencies are `esbuild` (bundling), `jsdom` (unit tests) and `@playwright/test` (browser tests).

## Project layout

| Path | What lives there |
| --- | --- |
| `src/geometry.js` | Pure scoring. No DOM access allowed here. |
| `src/targets.js` | Target discovery and editable-control key ownership. |
| `src/input.js` | Keymap, gamepad normalisation and poller. |
| `src/scroll.js` | Reveal-in-scroll-container logic. |
| `src/bridge.js` | `createDPadBridge` coordinator. |
| `dist/` | Generated by `npm run build`. **Commit it** (`npm test` fails if it is stale). |
| `types/index.d.ts` | Public TypeScript declarations. Update them with API changes. |
| `test/*.test.js` | `node:test` unit tests. `test/helpers/dom.js` is the jsdom geometry harness. |
| `test/e2e/` | Playwright specs against `examples/`. |

## Coding conventions

- Plain modern JavaScript (ES modules). No framework, no runtime dependencies, no network calls.
- Inside `src/`, derive `win` from `root.ownerDocument.defaultView` instead of using browser globals, so code stays testable and works across frames. The only global use is the convenience default (`document.body` when no `root` is given).
- Every listener must be registered through `listen()` in `bridge.js` (or have a matching disposer). `destroy()` must leave nothing behind, and the "destroy" tests check this.
- Don't `preventDefault` a key the SDK doesn't own. Typing, platform Back and media/voice keys must keep working.
- Deterministic behaviour: scoring changes need a tie-break story and a test.
- Keep functions small, name them by intent, and comment the *why* (as the existing code does).
- Formatting: 2-space indent, single quotes, semicolons, trailing commas in multiline literals.
- No invented numbers in docs: describe what was measured or tested, and how.

## Writing a test

Unit tests describe geometry with `data-rect="x,y,width,height"`. The harness stubs `getBoundingClientRect()` from it and subtracts the scroll offsets of `data-scroll` containers, as a browser would.

Example: suppose you want Right from the last card in a row to stop instead of wrapping:

```js
// test/my-feature.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { setup } from './helpers/dom.js';
import { createDPadBridge } from '../src/index.js';

test('Right at the end of a row is a boundary', () => {
  const env = setup(`
    <button id="a" data-rect="0,0,100,40">A</button>
    <button id="b" data-rect="120,0,100,40">B</button>`);
  const bridge = createDPadBridge({ root: env.document.body, gamepad: false }).mount();
  env.press('ArrowRight');
  env.press('ArrowRight');
  assert.equal(bridge.getFocused().id, 'b');
  bridge.destroy();
});
```

Run a single file with `node --test test/my-feature.test.js`. For behaviour that depends on real layout, CSS or browser focus rules, add a Playwright spec in `test/e2e/` that drives `examples/tv-demo` (the page exposes `window.__demo.bridge`).

## Pull requests

1. Branch from `main`. Keep one topic per PR.
2. `npm test && npm run test:e2e` must pass. Include `dist/` if `src/` changed (`npm run build`).
3. Update `README.md` / `docs/` / `types/` for user-visible changes.
4. Describe *what was tested and how*. Mention it if you tested on a real TV or gamepad, and which one.
